# 成果生命周期

## 状态定义

| 状态 | 中文名称 | 进入条件 | 退出条件 |
|---|---|---|---|
| `draft` | 草稿 | 已建立可打开或可运行的基础成果 | 核心评审范围和演示路径已明确 |
| `review` | 评审中 | 核心流程可完整演示，结构校验和运行检查通过 | 产品与业务评审形成明确结论 |
| `approved` | 已确认 | 产品与业务评审通过，最终 PRD 已完成并与成果对齐，遗留限制已记录 | 出现新一轮变更，或决定停止维护 |
| `archived` | 已归档 | 不再继续迭代，最后验证版本和原因已记录 | 原则上不再恢复；如恢复，应通过新的评审决定 |

## 基本原则

- 生命周期状态记录在成果的 `artifact.yaml` 中。
- 不通过移动目录表示状态，避免链接、脚本和历史路径失效。
- 状态代表产品成熟度，不代表运行状态。
- `draft` 成果也必须满足其类型的最低可用标准：HTML 可以打开，Demo 可以独立启动。
- `draft` 和 `review` 可以暂时不关联 PRD；`approved` 和 `archived` 必须通过 `product.requirement` 关联仓库内有效的最终 PRD。
- 状态变更通过 Pull Request 完成，并在说明中给出评审依据。

## 状态流转

```text
draft → review → approved → archived
```

评审未通过时，`review` 可以回到 `draft`。已确认成果发生重大范围变化时，应提高版本号并回到 `draft` 或 `review`，而不是覆盖原有确认记录。

## 版本要求

- 使用语义化版本 `MAJOR.MINOR.PATCH`。
- 进入 `approved` 前，最终 PRD 必须完成，并与原型或 Demo 的确认版本通过校验。
- 研发交底时应创建 `artifact/<artifact-id>/v<version>` 标签，作为交付基线。
- 不创建 `v1/`、`v2/`、`最终版/`等副本目录。
- `archived` 状态应记录最后一次成功运行日期、标签和归档原因。
